> Это рабочий план развития библиотеки (с 2026-10-02). **Не путать** с `Plan.md`, на который
> ссылаются комментарии в `SukiUI/ControlsAnimation/*` — это план исходного автора, он в
> репозиторий не попал.

## 1. Цель

Сделать SukiUI.Motion хорошей **самостоятельной** библиотекой анимаций для экосистемы Avalonia
(независимой от SukiUI), сохранив её сильные стороны: интерактивные пружины с переносом
скорости, арбитраж жестов, хореографии с settle-колбэками, нулевую стоимость простоя.

Исходная оценка (ревью 2026-10-02): как внутренний движок SukiUI — 7/10; как отдельная
библиотека — 4–5/10.

## 3. Правила работы (действуют во всех фазах)

- **R1. Ветка и remote.** Работа в форке `CiaranDall/SukiUI` (remote `fork`), ветка
  `motion/bugfixes` (для фаз 3–4 — решить, продолжать ли в ней или резать новые ветки).
  `origin` — upstream `kikipoulet/SukiUI`, туда не пушим.
- **R2. Никаких слепых фиксов.** Каждый баг: красный тест отдельным коммитом → исправление
  отдельным коммитом. Если тест не краснеет — баг опровергнут, код не трогаем.
- **R3. Перф-изменения — только с замером.** (Для фазы 3.) Сначала измерение «до», потом
  изменение, потом «после». Без цифр не оптимизируем.
- **R4. Находки — в ENGINEERING_NOTES.md.** Любая неочевидная особенность Avalonia/движка/обвязки
  фиксируется там с источником (файл + тег Avalonia) и следствием для нас.
- **R5. Решения — в этот файл** (раздел 6), с датой, альтернативами и обоснованием.
- **R6. Playground — отдельный проект**, ссылается только на SukiUI.Motion, только публичный API.
- **R7. Сборка всего решения** (`Suki.sln`) после изменений движка — SukiUI и Demo не должны ломаться.

## 6. Журнал решений

Формат: **ID — дата — решение.** Контекст → альтернативы → почему так → последствия.

### D1 — 2026-10-02 — Работаем в форке, отдельная ветка
- Контекст: пользователь попросил вести работу в своём форке.
- Решение: remote `fork` = `CiaranDall/SukiUI`, ветка `motion/bugfixes`; push только туда.

### D2 — 2026-10-02 — «Красный тест → фикс», двумя коммитами
- Контекст: пользователь требует доказательства на деле, не слепые фиксы, и хочет проверять сам без UI.
- Альтернативы: один коммит с тестом и фиксом (проверить «до» нельзя); тест + фикс без коммитов.
- Решение: test-коммит (красный) + fix-коммит (зелёный). Пользователь проверяет `git checkout <test>`
  + `dotnet test`.
- Последствие: в истории ветки есть красные коммиты — при слиянии можно squash.
- Исключение: баг 1 (тест и фикс одним коммитом — правило введено после него; «до» показано в чате).

### D3 — 2026-10-02 — Тестовая точка подмены часов: `internal static Func<TimeSpan>? SukiTicker.ClockOverride`
- Контекст: время движка — `Stopwatch`; без подмены тесты на реальных паузах = нестабильны.
- Альтернативы: публичный `IClock` (это API-решение — отложено в A10); подмена ещё и источника
  кадров (не понадобилась: headless `ForceRenderTimerTick` обслуживает RAF).
- Решение: минимальная internal-точка, видна только `SukiUI.Motion.Tests` (InternalsVisibleTo).
  `null` в продакшене — поведение не меняется. Инструментация (`TotalDispatchMs`) всегда меряет
  реальное время.
- Последствие: статическое поле → параллельность тестов отключена.

### D4 — 2026-10-02 — Тестовый стек: xUnit v3 + Avalonia.Headless.XUnit 12.1.1, net10.0
- Контекст: `Avalonia.Headless.XUnit 12.1.1` зависит от xunit.v3 3.2.2 (не xunit 2.x).
- Решение: `OutputType=Exe`, `<Using Include="Xunit"/>`, версии в `Directory.Packages.props`.
  Виртуальные кадры: `MotionHarness` (тик рендер-таймера + `RunJobs`), `Dispose` прокачивает 3 кадра
  (см. NOTES 2.2).

### D5 — 2026-10-02 — Playground отдельным проектом, только SukiUI.Motion и только публичный API
- Контекст: пользователь попросил не в Demo, а отдельно.
- Решение: `SukiUI.Motion.Playground` (код без XAML), одна сцена на баг, `TraceView` (график значения),
  статистика тикера. Собирается и со старым движком (`c2bf6bcae`) → сравнение «до/после» глазами.
  `PlaygroundSmokeTests` строит все сцены и жмёт все кнопки.
- Последствие: тестовый проект ссылается на playground.

### D6 — 2026-10-02 — Баг 2: минимальный фикс сейчас, политика арбитража — в фазе 4
- Решение: другая пружина во время пружины **перехватывает** канал с переносом позы и скорости
  (взведённый kick важнее); та же пружина повторно — только `Retarget` (release + capture-lost у кнопки).
- Почему: исправляет реальный дефект, не меняя модели; полноценная политика — A4.

### D7 — 2026-10-02 — Баг 6: подтвердить сейчас, исправлять в фазе 4
- Почему: переход на `BindingPriority.Animation` + очистка меняет семантику (тост `MaxHeight`,
  удерживаемые позы, копии эффектов из D10). Требует дизайна.
- Состояние: тесты `StylePriorityTests` с `Skip` и причиной (красноту показали до пометки).

### D8 — 2026-10-02 — Баг 5: хореография на отсоединённом элементе завершается мгновенно
- Альтернативы: молчаливый no-op (утечка: settle не выполнится → тост не удалится, попап не скроется);
  исключение (было).
- Решение: участники → конечная поза, затем `Then`.

### D9 — 2026-10-02 — Новый публичный `virtual void Program.Complete()`
- Для D8. Публичный, т.к. `Program` уже рассчитан на пользовательские типы программ.
  Базовая реализация — только `Done = true`. Реализации: Timed, Spring, Chain (отложенный release или
  последний шаг), Derived, Cascade (Reset).

### D10 — 2026-10-02 — Баг 7: движок мутирует только свои эффекты (`OwnedEffects`)
- Факт: значение сеттера стиля — один экземпляр на все контролы (NOTES 3.1).
- Решение: чужой эффект копируется в собственный экземпляр (поза сохраняется).
- Компромисс: копия ставится LocalValue → поздние изменения эффекта в стиле не дойдут (семейство бага 6, A5).

### D11 — 2026-10-02 — Баг 9: модель владения каналом
- Решение: `_active` — единственный источник владения; `Run` снимает подписку канала; `Stop` хореографии
  замораживает участников (`Freeze`) — поза/скорость доступны, `Offer` не блокируется; хореография не
  продвигает участника перехваченного канала (`Owns`). Подробно — NOTES 4.2.
- Известное ограничение: `Chain` с `Handoff` внутри хореографии (A8).

### D12 — 2026-10-02 — Баг 10: подшаг `min(8 мс, 1/max(ω, decay))`; `Spring` валидирует параметры
- Почему 1/max: при `ω·h ≤ 1` и `decay·h ≤ 1` матрица шага полунеявного Эйлера устойчива.
  Все профили SukiUI остаются на 8 мс → их траектории численно не изменились.
- `Spring` бросает `ArgumentOutOfRangeException` на нефинитные или ≤ 0 параметры; `default(Spring)`
  падает в `Start` с понятным сообщением. `record struct` переписан с явным конструктором и get-only
  свойствами (`with` больше не обходит валидацию), `Deconstruct` сохранён.

### D13 — 2026-10-02 — Баг 11: точное решение для всех трёх режимов; видимое изменение принято
- Передемпфированная ветка записана через экспоненты отрицательных показателей (без cosh/sinh) —
  без переполнения.
- Видимое изменение: большие диалоги (ζ 1.05 / 1.3) стартуют медленнее → A14.

### D14 — 2026-10-02 — Баг 12: окно зажима включает позу первого старта; сам зажим пока оставлен
- Альтернатива: убрать зажим целиком — меняет ощущение нажатия; это A6.

### D15 — 2026-10-02 — Баг 4: отложенная хореография помнит намерение хоста
- `Play` сбрасывает отложенную; при откладывании запоминается `isHostOpen()`; если к запуску оно
  изменилось — отбрасывается; `StartPending` сначала останавливает текущую.

### D16 — 2026-10-02 — Баг 14: `Simulate` — no-op, если motion не включён
- Проверено: бенчмарк `PressStressPage` включает motion через стиль темы → не затронут.
  `EnsureMover` удалён.

### D17 — 2026-10-02 — Документы контекста: PLAN.md, STATUS.md, ENGINEERING_NOTES.md в `SukiUI.Motion/`
- По просьбе пользователя: «чтобы не потерять контекст»; решения — детально.

### D18 — 2026-10-02 — ✅ ПРИНЯТО пользователем (2026-10-02): гибрид, Composition — опциональный бэкенд для трансформов
- Контекст: фаза 2, факты — ENGINEERING_NOTES §7, живые проверки — сцены C1–C4.
- Альтернативы:
  1. **Не использовать Composition.** Просто, но анимации дёргаются ровно тогда, когда UI-поток занят
     (открытие диалога/страницы, попап с длинным списком, приход тоста во время загрузки).
  2. **Перенести всё на Composition.** Невозможно: blur/тень, произвольные свойства и layout-свойства
     не анимируются на сервере (§7.3); нет чтения значений и событий завершения (§7.5–7.6).
  3. **Гибрид (предлагается).** UI-поток остаётся основным бэкендом (любое свойство, эффекты,
     производные каналы). Для каналов трансформов (Scale/ScaleX/ScaleY, TranslateX/Y, Rotate) — опциональный
     composition-бэкенд за тем же API `Channel`.
- Как устроен composition-бэкенд:
  - На UI-потоке — **аналитическая модель** траектории: timed = easing(t); пружина = точное решение
    уравнения с начальной позой и скоростью (не интегратор). Модель отвечает на `Value`/`Velocity` в
    любой момент и знает длительность до settle.
  - На старт/перенацеливание/прерывание — **один** keyframe на сервер: easing = нормированная кривая
    модели (неизменяемый объект), длительность = до settle. Поза при прерывании продолжается сервером,
    скорость — моделью.
  - Settle и `Then` — по таймеру UI-потока на известную длительность; покадровой работы на UI-потоке нет.
  - Производные каналы (motion blur от скорости) остаются на UI-тиках — под нагрузкой они будут
    дёргаться, трансформ — нет.
- Что НЕ делаем: `Offset`/`Size` (перезаписывает layout), `CompositionCustomVisual` как носитель
  интегратора (§7.9). `Opacity` — только после отдельного решения: её перезаписывает `Visual.Opacity` (§7.4).
- Предпосылки и риски:
  - Точный решатель пружины (с v0) — полезен и для UI-бэкенда; меняет численно траектории профилей SukiUI
    (сейчас полунеявный Эйлер) — оценить глазами.
  - Два мира трансформов: `RenderTransform` (видит `TranslatePoint`) и composition (видит хит-тест) — §7.7.
  - Тесты: серверные значения не наблюдаемы → тестировать модель; для пиксельной проверки — headless со
    Skia (`CaptureRenderedFrame`) — проверить осуществимость.
  - Привязка к внутреннему поведению Avalonia (`TODO: dirty mask` может поменять семантику §7.4) →
    характеризующие тесты/сцены при обновлении Avalonia.
  - Задержка старта ~1 кадр (§7.6).
- Порядок, если принимаем: прототип на одном канале (Scale кнопки или открытие диалога) → замер (R3):
  стабильность при занятом UI-потоке и CPU на кадр → решение о масштабировании.
- Уточнения после проверки пользователем сцен C1–C2 (2026-10-02):

### D21 — 2026-10-02 — Прототип composition-бэкенда: устройство
- Цель прототипа (из D18): доказать на деле (1) плавность под нагрузкой UI-потока, (2) прерывание
  пружины с переносом скорости без рывка, (3) меньшую стоимость UI-потока — и только потом решать о
  масштабировании (R3).
- **Отдельный экспериментальный API, не встраиваем в `Channel` сейчас.** `CompositionChannel` для
  TranslateX, TranslateY, Scale — методы `SpringTo`, `EaseTo`, `Value`/`Velocity` по модели, событие
  завершения. Помечен `[Experimental("SUKIMOTION001")]`. Почему: прототип не должен рисковать
  исправленным движком; единый API `Channel` с выбором бэкенда — задача фазы 4 (A4, A2).
- **Модель траектории — аналитическая**, не интегратор:
  - пружина: точное решение для отклонения `d(t)` с `d0`, `v0` (недо-, критически и передемпфированная),
    скорость — аналитическая производная; длительность до settle — по огибающей (консервативно);
  - timed: `lerp(from, to, ease(t/T))`, скорость — численная производная.
- **Передача на сервер — плотные keyframe-ы (piecewise-linear), шаг 4 мс, линейный easing.**
  Альтернатива «один keyframe + easing = нормированная кривая» отвергнута: вырождается при
  `target == x0` (удар с места — тряска диалога), теряет точность при малом размахе, а у
  `Vector3D` одна кривая на все оси (X и Y с разными траекториями не выразить). Плотные кадры
  обобщаются на любые оси и любые кривые; ошибка линейной интерполяции при 4 мс — доли пикселя.
  Первый сегмент идёт от текущего серверного значения (непрерывность позы при прерывании и сглаживание
  задержки коммита, NOTES §7.6).
- **Оси одного свойства собираются вместе:** TranslateX и TranslateY — одно свойство `Translation`
  (Vector3D) → при старте любой оси анимация `Translation` пересобирается из моделей обеих осей на общей
  сетке времени. Так же Scale (X, Y).
- **Завершение:** таймер UI-потока на длительность траектории; покадровой работы на UI-потоке нет.
- **Отсоединение:** composition-визуал при detach может пропасть — при attach заново ставим позу покоя
  из модели.
- **Порядок трансформов** (NOTES §7.8): composition Scale/Rotation применяются **после**
  `RenderTransform`, Translation — последним. Смешение с UI-каналами rotate/skew меняет порядок — в
  прототипе не смешиваем; учесть в фазе 4.
- **Проверка (критерии приёмки прототипа):**
  - юнит-тесты модели: точное решение против интегратора, непрерывность скорости при прерывании,
    длительность до settle;
  - пиксельные тесты: доезжает до цели (EaseTo, SpringTo), прерывание без скачка, порядок трансформов;
  - сцена playground + замер: плавность при занятом UI-потоке; стоимость UI-потока на N объектов
    (движок против прототипа).

### D22 — 2026-10-02 — Адаптивная сетка ключевых кадров вместо фиксированного шага 4 мс
- Контекст: замер (NOTES §7.14) показал, что фиксированный шаг 4 мс нагружает UI-поток при запусках
  сильнее, чем движок покадрово (67 против 22 мс/с при 200 объектах) — ~1000+ кадров на пружину ζ=0.3.
- Решение: `KeyFrameGrid` — шаг `sqrt(8·tol/|a|)`, ограничен [1 мс, 100 мс], ускорение проверяется в начале,
  середине и конце шага (у колеблющейся пружины ускорение проходит через ноль). Допуск: 0.25 DIP для
  сдвига, 0.0025 для масштаба. Ускорение — новый член `ICurve.Acceleration` (у пружины — точно из уравнения).
- Гарантия: допуск держится при `|a| ≤ 8·tol/MinStep²` (2·10⁶ DIP/с²) — все реалистичные пружины; более
  жёсткие завершаются за кадр-два и попадают в цель точно (тест `Sub_frame_spring_still_lands_exactly`).
- Проверено: `KeyFrameGridTests` меряют реальную ошибку интерполяции плотно (не доверяя оценке); пиксельные
  тесты прототипа зелёные. Замер: UI-поток на запуски 67 → 15 мс/с (200 шт.), 175 → 47 мс/с (600 шт.).

### D23 — 2026-10-02 — Прототип: пуш и время старта — в момент коммита; `CommitAsync()` для вызывающего кода
- Контекст: пользователь в сцене P1 увидел, что «composition тоже замирает» при запуске + сне в одном
  обработчике. Замер `--measure-stall` (NOTES §7.15) подтвердил: старт уходит на сервер только с коммитом,
  а коммит выполняет UI-поток. Плюс баг прототипа: кривые отсчитывались от вызова и убегали от экрана на
  весь сон, завершение срабатывало рано (красный тест `Curve_is_retimed_to_the_commit_after_a_stall`:
  нарисовано 52 px, модель 156.6).
- Отвергнуто: метка времени с потока рендера по `Batch.Processed` — в headless обработка ждёт тика рендера,
  сдвиг ложный (180 мс), ломал инерцию при прерывании (поймано тестом прерывания).
- Решение: `Start()` только помечает свойство «грязным»; ключевые кадры строятся в
  `Compositor.RequestCompositionUpdate` (колбэк прямо перед коммитом). Кривые, запущенные с прошлого
  коммита, стартуют в этот момент (до коммита кривая «стоит» на начале: `Value` = стартовая поза),
  таймер завершения взводится от него же. Побочный плюс: в коммит уходит итоговое состояние хода
  (`SpringTo` + `Pose` в одном обработчике → только поза).
- `CompositionMotion.CommitAsync()` = `RequestCommitAsync()` по умолчанию — для кода, которому после запуска
  нужно занять UI-поток. Это **ограничение подхода**, не баг: без коммита composition не поможет.
- Известное ограничение: прерывание прямо перед долгим сном — сервер всё это время доигрывает старую
  анимацию, а новая кривая стартует с позы на момент вызова; на экране непрерывно (старт от текущего
  серверного значения), модель — с небольшим расхождением до конца первого сегмента.
- Тест прерывания сделан независимым от точности реальных пауз (сравнение с моделью в тот же момент);
  инерцию через переключение точно проверяет `CurveTests`. 5 полных прогонов подряд — зелёные.

### D25 — 2026-10-02 — P8: порог остановки пружины по единице канала
- Замер (NOTES §8.2): для каналов в DIP абсолютный порог 0.0005 держит цикл кадров на 40 % дольше видимого
  движения (P1-пружина: 104 лишних кадра из 254).
- Отвергнуто: относительный порог (доля от пути) — для коротких ходов он становится грубым, для длинных
  тоньше нужного, а видимость определяется пикселями, не долей пути. Порог «по пикселям» требует размера
  элемента — лишняя связь для масштаба.
- Решение: `internal SettleThreshold` у канала — DIP: 0.05 / 2; градусы: 0.01 / 0.4; безразмерные и
  `Property(...)`: прежние 0.0005 / 0.02. Отношение скорость/позиция = 40, как было. Тот же порог — в
  `SpringCurve` прототипа. Публичная настройка — фаза 4 (A16).
- Видимое изменение: финальный «прыжок» на цель до 0.05 DIP вместо 0.0005 — ниже порога различимости.
