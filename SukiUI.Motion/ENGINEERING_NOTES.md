# SukiUI.Motion — инженерные заметки

Неочевидные особенности Avalonia, движка и тестовой обвязки, найденные по ходу работы.
Каждая запись: **факт → источник → что это значит для нас**.

Версия Avalonia на момент записей: **12.1.1**. При обновлении Avalonia — перепроверять
записи с пометкой источника в исходниках Avalonia.

---

## 1. Avalonia: кадровый цикл и `RequestAnimationFrame`

### 1.1. RAF глобален, а не per-TopLevel

- **Факт.** `TopLevel.RequestAnimationFrame(cb)` только проверяет поток и пересылает вызов в
  `MediaContext.Instance.RequestAnimationFrame` — один `MediaContext` на UI-поток, одна
  очередь колбэков на все окна.
- **Источник.** `src/Avalonia.Controls/TopLevel.cs` (`RequestAnimationFrame`),
  `src/Avalonia.Base/Media/MediaContext.Clock.cs`.
- **Для нас.** «Один цикл на TopLevel» в `SukiTicker` — это N регистраций в одной глобальной
  очереди при N окнах. Корректно, но разбиение по TopLevel не даёт изоляции по времени кадра:
  все окна пульсируют в одном `Render()`.

### 1.2. Как RAF перевзводится изнутри кадра

- **Факт.** `RequestAnimationFrame` = `ScheduleRender(false)` + постановка в очередь.
  Во время `Render()` поле `_nextRenderOp` ещё не обнулено, поэтому новый RAF **не ставит**
  новый проход рендера. Следующий кадр приходит одним из двух путей (конец `RenderCore`):
  1. кадр что-то изменил → коммит в композитор → по завершении пакета
     (`CompositionBatchFinished`) → `ScheduleRender` — темп композитора / vsync;
  2. ничего не изменил → `_animationsTimer`: `DispatcherTimer` на **16 мс реального времени**.
- **Источник.** `src/Avalonia.Base/Media/MediaContext.cs` (`ScheduleRender`, `Render`,
  `RenderCore`), `MediaContext.Compositor.cs` (`CommitCompositorsWithThrottling`,
  `CompositionBatchFinished`).
- **Для нас.**
  - Подписчик тикера, который ничего не пишет, крутится на темпе `DispatcherTimer`, а не vsync.
    Каналы движка пишут каждый кадр, поэтому в норме идут по пути (1). Комментарий в
    `SukiTicker` про «prime the pump» верен по сути.
  - Троттлинг: пока предыдущий пакет композиции не обработан, новый коммит не уходит —
    при тяжёлом рендере кадры анимации пропускаются (позы считаются по абсолютному времени,
    так что траектории не «замедляются», а прореживаются; пружины ограничены `dt ≤ 50 мс`).

### 1.3. Время кадра

- **Факт.** RAF передаёт в колбэк `_time.Elapsed` контекста на момент `Render()`.
  `SukiTicker` этот аргумент игнорирует и берёт `Stopwatch` в момент вызова подписчиков.
- **Источник.** `MediaContext.Clock.cs` (`Pulse(now)`), `SukiUI.Motion/SukiTicker.cs`.
- **Для нас.** Кандидат в раздел производительности (джиттер позы относительно кадра).

## 2. Avalonia.Headless: тестирование анимаций

### 2.1. Прокачка кадров

- **Факт.** По умолчанию `ShouldRenderOnUIThread = true` → `HeadlessRenderTimer`;
  `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` синхронно тикает рендер, затем
  `Dispatcher.UIThread.RunJobs()` выполняет `CompositionBatchFinished` → `Render()` → RAF.
  Итог: **один вызов подписчика на один `Frame()`**, если подписчик пишет визуальное свойство.
- **Источник.** `src/Headless/Avalonia.Headless/AvaloniaHeadlessPlatform.cs`;
  проверено тестом `HarnessTests.Ticker_runs_one_callback_per_pumped_frame_on_virtual_time`.
- **Для нас.** Тесты должны анимировать то, что реально пишет свойства. Подписчик «без
  записи» в headless после первого кадра замирает (путь 1.2-(2) идёт по реальному времени).

### 2.2. Общее состояние между тестами

- **Факт.** `MediaContext` — синглтон на всю тестовую сессию. Незавершённые RAF-регистрации
  и пакеты композиции от предыдущего теста влияют на следующий (наблюдали недетерминированный
  провал, зависящий от порядка тестов).
- **Для нас.** `MotionHarness.Dispose` прокачивает 3 кадра перед закрытием окна.
  Параллельность тестов отключена: `SukiTicker.ClockOverride` — статическое поле.

### 2.3. Пакеты

- `Avalonia.Headless.XUnit 12.1.1` зависит от **xunit.v3 3.2.2** (не xunit 2.x):
  тестовый проект — `OutputType=Exe`, `using Xunit` подключается явно (`<Using Include="Xunit" />`).

## 3. Avalonia: стили, шаблоны, попапы

### 3.1. Значение сеттера стиля — один экземпляр на все контролы

- **Факт.** `new Setter(Visual.EffectProperty, new DropShadowEffect())` в стиле отдаёт **один и
  тот же** объект каждому контролу, который матчит стиль (`Assert.Same(first.Effect, second.Effect)`).
  Мутация такого объекта меняет все контролы сразу.
- **Источник.** Проверено тестом `EffectSlotTests` (предусловие).
- **Для нас.** Движок мутирует на месте только объекты, созданные им самим
  (`OwnedEffects`); чужие — копирует. Правило общее для любых мутабельных значений из стилей
  (эффекты, трансформации, кисти) и для будущих каналов.

### 3.2. Fluent `ComboBox`: `PART_Popup.IsOpen` связан TwoWay с `IsDropDownOpen`

- **Факт.** В шаблоне Fluent: `IsOpen="{TemplateBinding IsDropDownOpen, Mode=TwoWay}"`,
  корень попапа — `Border x:Name="PopupBorder"`.
- **Источник.** `src/Avalonia.Themes.Fluent/Controls/ComboBox.xaml` (12.1.1).
- **Для нас.** На стоковом шаблоне `Popup.IsOpen` — ненадёжный свидетель в тестах (его
  перетирает привязка). В SukiUI motion владеет попапом сам (привязки нет). В тестах
  свидетель — сама хореография (счётчик в `Then`).

### 3.3. Шаблонные части не видны в момент `TemplateApplied`

- **Факт.** В обработчике `TemplateApplied` обход `GetTemplateDescendants()` ещё не находит
  части внутри попапа: стадия не резолвится, отложенная хореография остаётся отложенной до
  следующего логического присоединения или `Play`. Комментарий в `PopupHandle.Play` об этом
  верен.
- **Источник.** Проверено тестом `PopupPendingTests`: 4a воспроизводится только через
  повторное присоединение (переключение вкладки).
- **Для нас.** Любая логика «на TemplateApplied» должна иметь страховку на attach или первый вызов.

### 3.4. Шаблонный `Popup` не в логическом дереве хоста

- **Факт.** `Popup` из шаблона `ComboBox` не находится через `GetLogicalDescendants()` хоста —
  только через `GetTemplateDescendants()`.
- **Для нас.** Резолверы частей — только через шаблонный обход (как и делает движок).

## 4. Движок SukiUI.Motion: поведение под капотом

### 4.1. `Channel.Value` читает состояние движка, а не экран

- **Факт.** Каналы трансформаций читают значения из своего блока (`Transforms.Block`), а не из
  фактического `RenderTransform` элемента. Если блок рассинхронизирован с экраном, `Value`
  врёт. Именно так проявлялся баг 1: `Value == 10`, на экране 0.
- **Для нас.** В тестах проверять **итоговую матрицу** `RenderTransform.Value`, а не только
  `Channel.Value`.

### 4.2. Модель владения каналом (после бага 9)

- Единственный источник правды «кто владеет каналом» — `Channel._active`.
- `Offer` (триггеры) — правила арбитража; канал сам подписан на тикер.
- `Run` (хореографии) — принудительный захват: канал **снимает свою подписку**, драйвер —
  хореография.
- `Choreography.Stop` → участники **замораживаются** (`Channel.Freeze`): поза и скорость
  доступны вытесняющей программе, но `Offer` канал больше не блокирует.
- Хореография не продвигает участника, чей канал перехватили (`Channel.Owns`).
- Ограничение: `Chain` с `Handoff` внутри хореографии не поддержан (отложенную пружину
  отпускания никто не продвигает) — кандидат на этап API.

### 4.3. Окно зажима позы (`_seenMin/_seenMax`)

- Окно растёт из всех целей и From, а после бага 12 — ещё и из позы первого старта канала.
- Пружина и `Chain` зажимают стартовую позу в окно; `TimedTrajectory` — нет (несогласованно).
- Побочный эффект: пружина, перелетевшая за пределы окна и прерванная нажатием, стартует с
  зажатой позы — возможен рывок. **Вопрос на этап API:** нужен ли зажим вообще.

### 4.4. Отсоединённый хост: хореография завершается мгновенно

- Без TopLevel кадров не будет: `Choreography.Start` переводит участников в конечное состояние
  (`Program.Complete()`) и выполняет `Then`. Иначе утекает то, что зависит от settle
  (удаление тоста, закрытие попапа).
- Защиты «нет TopLevel — не стартовать» в потребителях (`SukiToggleSwitchMotion.Pose`,
  `SukiToastMotion.TickOwner`) теперь избыточны, но безвредны.

### 4.5. Устойчивость интегратора

- Полунеявный Эйлер устойчив, пока `ω·h` и `decay·h` порядка < 2. Подшаг теперь
  `min(8 мс, 1/max(ω, decay))`. Все профили SukiUI (`max(ω, decay) ≤ 53.4`) остаются на 8 мс —
  траектории численно не изменились.
- Сильно передемпфированная пружина (ζ ≫ 1) физически медленная: медленная мода
  `r = −a + √(a² − ω²)`. Пример: ω=30, decay=400 → постоянная времени ≈ 0.44 с.

### 4.6. Имя `Program` конфликтует с точкой входа приложения

- **Факт.** В любом приложении есть `static class Program`. В playground он перекрыл
  `SukiUI.Motion.Program` — понадобился алиас `using MotionProgram = SukiUI.Motion.Program`.
  Плюс в SukiUI 4 алиаса `using Motion = SukiUI.Motion.Motion` (имя класса = имя namespace).
- **Для нас.** Довод для переименований на этапе API.

### 4.7. Реальное влияние багов на SukiUI (не только теория)

- **Баг 3** бил по `SukiToggleSwitchMotion`: он перезапускает одну и ту же хореографию на
  каждое изменение `IsChecked` — каждое переключение на лету оставляло вечную подписку
  (движок будил UI-поток ~60 раз/с навсегда).
- **Баг 9** — сценарий `SukiTypingMotion`: hover-проба через `Offer`, удар клавиши через
  хореографию на том же канале → два драйвера.
- **Баг 12** — `SukiTypingMotion` уже содержал обход (`energy.Track(0.0); energy.Track(1.0)`).
- **Баг 11** — диалог: `SukiSpringEaseOut` с ζ = 1.05 (по умолчанию) и 1.3 (альтернативный
  профиль). Профили подбирались на старой кривой: после исправления большие диалоги чуть
  медленнее стартуют при открытии. Профили стоит перепроверить глазами.

## 5. Открытые вопросы на этап API

1. **Приоритет записи (баг 6).** Писать с `BindingPriority.Animation` и очищать по окончании?
   Что значит «конец» для удерживаемой позы (hover держит 1.06)? Как это сочетается с
   `MaxHeight` у тоста и с копиями эффектов (баг 7 ставит копию как LocalValue)?
   Порядок приоритетов в Avalonia 12 перепроверить по исходникам перед решением.
2. **Арбитраж по типам программ** (`Chain` = нажатие, `Spring` = отпускание, `Timed` = hover)
   → явная политика приоритетов и прерывания.
3. **Окно зажима позы** — оставить, сделать явным или убрать (см. 4.3).
4. **`Chain` внутри хореографии** (см. 4.2).
5. **Переименования:** `Motion` (класс = namespace), `Program`.
