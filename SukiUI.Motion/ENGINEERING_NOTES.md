# SukiUI.Motion — инженерные заметки

Неочевидные особенности Avalonia, движка и тестовой обвязки, найденные по ходу работы.
Каждая запись: **факт → источник → что это значит для нас**.

Версия Avalonia на момент записей: **12.1.1**. При обновлении Avalonia — перепроверять
записи с пометкой источника в исходниках Avalonia.

---

## 1. Avalonia: кадровый цикл и `RequestAnimationFrame`

### 1.1. RAF глобален, а не per-TopLevel

- **Факт.** `TopLevel.RequestAnimationFrame(cb)` только проверяет поток и пересылает вызов в
  `MediaContext.Instance.RequestAnimationFrame` — один `MediaContext` на UI-поток, одна
  очередь колбэков на все окна.
- **Источник.** `src/Avalonia.Controls/TopLevel.cs` (`RequestAnimationFrame`),
  `src/Avalonia.Base/Media/MediaContext.Clock.cs`.
- **Для нас.** «Один цикл на TopLevel» в `SukiTicker` — это N регистраций в одной глобальной
  очереди при N окнах. Корректно, но разбиение по TopLevel не даёт изоляции по времени кадра:
  все окна пульсируют в одном `Render()`.

### 1.2. Как RAF перевзводится изнутри кадра

- **Факт.** `RequestAnimationFrame` = `ScheduleRender(false)` + постановка в очередь.
  Во время `Render()` поле `_nextRenderOp` ещё не обнулено, поэтому новый RAF **не ставит**
  новый проход рендера. Следующий кадр приходит одним из двух путей (конец `RenderCore`):
  1. кадр что-то изменил → коммит в композитор → по завершении пакета
     (`CompositionBatchFinished`) → `ScheduleRender` — темп композитора / vsync;
  2. ничего не изменил → `_animationsTimer`: `DispatcherTimer` на **16 мс реального времени**.
- **Источник.** `src/Avalonia.Base/Media/MediaContext.cs` (`ScheduleRender`, `Render`,
  `RenderCore`), `MediaContext.Compositor.cs` (`CommitCompositorsWithThrottling`,
  `CompositionBatchFinished`).
- **Для нас.**
  - Подписчик тикера, который ничего не пишет, крутится на темпе `DispatcherTimer`, а не vsync.
    Каналы движка пишут каждый кадр, поэтому в норме идут по пути (1). Комментарий в
    `SukiTicker` про «prime the pump» верен по сути.
  - Троттлинг: пока предыдущий пакет композиции не обработан, новый коммит не уходит —
    при тяжёлом рендере кадры анимации пропускаются (позы считаются по абсолютному времени,
    так что траектории не «замедляются», а прореживаются; пружины ограничены `dt ≤ 50 мс`).

### 1.3. Время кадра

- **Факт.** RAF передаёт в колбэк `_time.Elapsed` контекста на момент `Render()`.
  `SukiTicker` этот аргумент игнорирует и берёт `Stopwatch` в момент вызова подписчиков.
- **Источник.** `MediaContext.Clock.cs` (`Pulse(now)`), `SukiUI.Motion/SukiTicker.cs`.
- **Для нас.** Кандидат в раздел производительности (джиттер позы относительно кадра).

## 2. Avalonia.Headless: тестирование анимаций

### 2.1. Прокачка кадров

- **Факт.** По умолчанию `ShouldRenderOnUIThread = true` → `HeadlessRenderTimer`;
  `AvaloniaHeadlessPlatform.ForceRenderTimerTick()` синхронно тикает рендер, затем
  `Dispatcher.UIThread.RunJobs()` выполняет `CompositionBatchFinished` → `Render()` → RAF.
  Итог: **один вызов подписчика на один `Frame()`**, если подписчик пишет визуальное свойство.
- **Источник.** `src/Headless/Avalonia.Headless/AvaloniaHeadlessPlatform.cs`;
  проверено тестом `HarnessTests.Ticker_runs_one_callback_per_pumped_frame_on_virtual_time`.
- **Для нас.** Тесты должны анимировать то, что реально пишет свойства. Подписчик «без
  записи» в headless после первого кадра замирает (путь 1.2-(2) идёт по реальному времени).

### 2.2. Общее состояние между тестами

- **Факт.** `MediaContext` — синглтон на всю тестовую сессию. Незавершённые RAF-регистрации
  и пакеты композиции от предыдущего теста влияют на следующий (наблюдали недетерминированный
  провал, зависящий от порядка тестов).
- **Для нас.** `MotionHarness.Dispose` прокачивает 3 кадра перед закрытием окна.
  Параллельность тестов отключена: `SukiTicker.ClockOverride` — статическое поле.

### 2.3. Пакеты

- `Avalonia.Headless.XUnit 12.1.1` зависит от **xunit.v3 3.2.2** (не xunit 2.x):
  тестовый проект — `OutputType=Exe`, `using Xunit` подключается явно (`<Using Include="Xunit" />`).

### 2.4. `DispatcherTimer` в headless не срабатывает от одного `RunJobs()`

- **Факт.** `Dispatcher.RunJobs()` переводит созревшие таймеры в очередь (`PromoteTimers`) **только
  после выполнения другой задачи** (`ExecuteJob → PromoteTimers`). На пустой очереди `RunJobs`
  сразу возвращается — таймеры не срабатывают никогда (проверено: таймеры 100…2000 мс — ни одного
  срабатывания за 3 с). «Иногда работает» — если в очереди случайно оказалась задача (рендер после
  захвата кадра).
- **Источник.** `src/Avalonia.Base/Threading/Dispatcher.Queue.cs` (`RunJobs`, `ExecuteJob`).
- **Для нас.** Обвязка ставит пустую задачу перед `RunJobs` (`Pixels.Pump`). После этого таймеры
  срабатывают точно (100 → 105 мс, 1300 → 1300 мс). Любой код движка на `DispatcherTimer`
  (завершение composition-каналов, fallback тикера) тестировать только через такой насос.

## 3. Avalonia: стили, шаблоны, попапы

### 3.1. Значение сеттера стиля — один экземпляр на все контролы

- **Факт.** `new Setter(Visual.EffectProperty, new DropShadowEffect())` в стиле отдаёт **один и
  тот же** объект каждому контролу, который матчит стиль (`Assert.Same(first.Effect, second.Effect)`).
  Мутация такого объекта меняет все контролы сразу.
- **Источник.** Проверено тестом `EffectSlotTests` (предусловие).
- **Для нас.** Движок мутирует на месте только объекты, созданные им самим
  (`OwnedEffects`); чужие — копирует. Правило общее для любых мутабельных значений из стилей
  (эффекты, трансформации, кисти) и для будущих каналов.

### 3.2. Fluent `ComboBox`: `PART_Popup.IsOpen` связан TwoWay с `IsDropDownOpen`

- **Факт.** В шаблоне Fluent: `IsOpen="{TemplateBinding IsDropDownOpen, Mode=TwoWay}"`,
  корень попапа — `Border x:Name="PopupBorder"`.
- **Источник.** `src/Avalonia.Themes.Fluent/Controls/ComboBox.xaml` (12.1.1).
- **Для нас.** На стоковом шаблоне `Popup.IsOpen` — ненадёжный свидетель в тестах (его
  перетирает привязка). В SukiUI motion владеет попапом сам (привязки нет). В тестах
  свидетель — сама хореография (счётчик в `Then`).

### 3.3. Шаблонные части не видны в момент `TemplateApplied`

- **Факт.** В обработчике `TemplateApplied` обход `GetTemplateDescendants()` ещё не находит
  части внутри попапа: стадия не резолвится, отложенная хореография остаётся отложенной до
  следующего логического присоединения или `Play`. Комментарий в `PopupHandle.Play` об этом
  верен.
- **Источник.** Проверено тестом `PopupPendingTests`: 4a воспроизводится только через
  повторное присоединение (переключение вкладки).
- **Для нас.** Любая логика «на TemplateApplied» должна иметь страховку на attach или первый вызов.

### 3.4. Шаблонный `Popup` не в логическом дереве хоста

- **Факт.** `Popup` из шаблона `ComboBox` не находится через `GetLogicalDescendants()` хоста —
  только через `GetTemplateDescendants()`.
- **Для нас.** Резолверы частей — только через шаблонный обход (как и делает движок).

## 4. Движок SukiUI.Motion: поведение под капотом

### 4.1. `Channel.Value` читает состояние движка, а не экран

- **Факт.** Каналы трансформаций читают значения из своего блока (`Transforms.Block`), а не из
  фактического `RenderTransform` элемента. Если блок рассинхронизирован с экраном, `Value`
  врёт. Именно так проявлялся баг 1: `Value == 10`, на экране 0.
- **Для нас.** В тестах проверять **итоговую матрицу** `RenderTransform.Value`, а не только
  `Channel.Value`.

### 4.2. Модель владения каналом (после бага 9)

- Единственный источник правды «кто владеет каналом» — `Channel._active`.
- `Offer` (триггеры) — правила арбитража; канал сам подписан на тикер.
- `Run` (хореографии) — принудительный захват: канал **снимает свою подписку**, драйвер —
  хореография.
- `Choreography.Stop` → участники **замораживаются** (`Channel.Freeze`): поза и скорость
  доступны вытесняющей программе, но `Offer` канал больше не блокирует.
- Хореография не продвигает участника, чей канал перехватили (`Channel.Owns`).
- Ограничение: `Chain` с `Handoff` внутри хореографии не поддержан (отложенную пружину
  отпускания никто не продвигает) — кандидат на этап API.

### 4.3. Окно зажима позы (`_seenMin/_seenMax`)

- Окно растёт из всех целей и From, а после бага 12 — ещё и из позы первого старта канала.
- Пружина и `Chain` зажимают стартовую позу в окно; `TimedTrajectory` — нет (несогласованно).
- Побочный эффект: пружина, перелетевшая за пределы окна и прерванная нажатием, стартует с
  зажатой позы — возможен рывок. **Вопрос на этап API:** нужен ли зажим вообще.

### 4.4. Отсоединённый хост: хореография завершается мгновенно

- Без TopLevel кадров не будет: `Choreography.Start` переводит участников в конечное состояние
  (`Program.Complete()`) и выполняет `Then`. Иначе утекает то, что зависит от settle
  (удаление тоста, закрытие попапа).
- Защиты «нет TopLevel — не стартовать» в потребителях (`SukiToggleSwitchMotion.Pose`,
  `SukiToastMotion.TickOwner`) теперь избыточны, но безвредны.

### 4.5. Устойчивость интегратора

- Полунеявный Эйлер устойчив, пока `ω·h` и `decay·h` порядка < 2. Подшаг теперь
  `min(8 мс, 1/max(ω, decay))`. Все профили SukiUI (`max(ω, decay) ≤ 53.4`) остаются на 8 мс —
  траектории численно не изменились.
- Сильно передемпфированная пружина (ζ ≫ 1) физически медленная: медленная мода
  `r = −a + √(a² − ω²)`. Пример: ω=30, decay=400 → постоянная времени ≈ 0.44 с.

### 4.6. Имя `Program` конфликтует с точкой входа приложения

- **Факт.** В любом приложении есть `static class Program`. В playground он перекрыл
  `SukiUI.Motion.Program` — понадобился алиас `using MotionProgram = SukiUI.Motion.Program`.
  Плюс в SukiUI 4 алиаса `using Motion = SukiUI.Motion.Motion` (имя класса = имя namespace).
- **Для нас.** Довод для переименований на этапе API.

### 4.7. Реальное влияние багов на SukiUI (не только теория)

- **Баг 3** бил по `SukiToggleSwitchMotion`: он перезапускает одну и ту же хореографию на
  каждое изменение `IsChecked` — каждое переключение на лету оставляло вечную подписку
  (движок будил UI-поток ~60 раз/с навсегда).
- **Баг 9** — сценарий `SukiTypingMotion`: hover-проба через `Offer`, удар клавиши через
  хореографию на том же канале → два драйвера.
- **Баг 12** — `SukiTypingMotion` уже содержал обход (`energy.Track(0.0); energy.Track(1.0)`).
- **Баг 11** — диалог: `SukiSpringEaseOut` с ζ = 1.05 (по умолчанию) и 1.3 (альтернативный
  профиль). Профили подбирались на старой кривой: после исправления большие диалоги чуть
  медленнее стартуют при открытии. Профили стоит перепроверить глазами.

## 7. Avalonia Composition API (фаза 2)

Источники — исходники Avalonia **12.1.1**: `src/Avalonia.Base/Rendering/Composition/**`,
`src/Avalonia.Base/composition-schema.xml` (схема свойств, по ней генерируется код),
`src/tools/DevGenerators/CompositionGenerator/Generator.cs` (шаблоны сеттеров),
`src/Avalonia.Base/Visual.Composition.cs`, `src/Avalonia.Base/VisualExtensions.cs`.
Живые проверки — сцены **C1–C4** в playground (headless их показать не может: там рендер на
UI-потоке, а серверные значения не читаются).

### 7.1. Что это

- Avalonia 11+ рисует через **композитор**. UI-поток держит «клиентское» дерево
  `CompositionVisual` (у каждого `Visual` есть свой), изменения пакетами (batch) уходят на
  «сервер» композиции, который рисует кадры.
- Публичный вход: `ElementComposition.GetElementVisual(visual)` → `CompositionVisual`
  (есть только пока элемент присоединён). Анимации: `compositor.Create{Scalar|Double|Vector3D|…}KeyFrameAnimation()`,
  `CreateExpressionAnimation`, `CreateImplicitAnimationCollection`, `CreateAnimationGroup`;
  запуск — `visual.StartAnimation("Имя", anim)`, остановка — `StopAnimation`.
- Ещё: `CompositionCustomVisual` + `CompositionCustomVisualHandler` — свой визуал с колбэками
  на потоке рендера (`OnAnimationFrameUpdate`, `OnRender`, `OnMessage`).

### 7.2. Поток

- **Факт.** Win32: `Win32PlatformOptions.ShouldRenderOnUIThread = false` по умолчанию → таймер
  рендера `SleepLoopRenderTimer` на отдельном потоке. Composition-анимации вычисляются на сервере
  (`KeyFrameAnimationInstance.Evaluate`) — **UI-поток для них не нужен**.
- Headless по умолчанию рендерит на UI-потоке → независимость от UI-потока в тестах не видна.
- **Не проверено:** браузер (WASM) и мобильные платформы — какая там модель потоков.
- **Проверка:** сцена C1 (UI-поток спит 1.5 с: SukiUI.Motion замирает, composition — нет).

### 7.3. Что можно анимировать

- **Публичные анимируемые** свойства `CompositionVisual`: `Visible`, `Opacity`, `ClipToBounds`,
  `Offset`, `Translation`, `Size`, `AnchorPoint`, `CenterPoint`, `RotationAngle`, `Orientation`
  (кватернион), `Scale`.
- **Internal / не анимируются:** `TransformMatrix` (сюда кладётся `RenderTransform`), `Effect`
  (blur/тень), `Clip`, `OpacityMask`.
- Типы keyframe-анимаций: Scalar, Double, Boolean, Color, Vector, Vector2, Vector3, Vector3D,
  Vector4, Quaternion. (`Color` анимирует `CompositionSolidColorVisual.Color`, не кисть элемента.)
- **Для нас:** на поток рендера можно перенести только трансформы и прозрачность. Blur, тень,
  произвольные `AvaloniaProperty` (`TypingIntensity`, `OverlayOpacity`), layout-свойства
  (`MaxHeight`) — только UI-поток.

### 7.4. Синхронизация `Visual` → `CompositionVisual` перезаписывает часть свойств

- **Факт.** `Visual.SynchronizeCompositionProperties` при каждой пометке визуала «грязным» пишет
  `Offset` (позиция из layout), `Size`, `Visible`, `Opacity`, `ClipToBounds`, `Clip`,
  `OpacityMask`, `CacheMode`, `Effect`, `TransformMatrix` (из `RenderTransform`). В коде прямо
  стоит `TODO: Introduce a dirty mask`.
- **Факт.** Клиентский сеттер пишет только если значение **изменилось** (`field != value`), а
  клиентское поле хранит последнее значение, записанное с UI-потока, не анимированное.
  Запись **снимает** анимацию свойства (клиент: `PendingAnimations.Remove`; сервер:
  `SetAnimatedValue → RemoveAnimationForProperty`).
- **Следствия:**
  - `Translation`, `Scale`, `RotationAngle`, `Orientation`, `CenterPoint` синхронизация не трогает —
    **безопасны**.
  - `Opacity` переживает перерисовки, но **обрывается**, как только меняется `Visual.Opacity`
    (стиль `:disabled`, класс, код). После окончания анимации экран ≠ `Visual.Opacity` — свойство
    на UI-потоке «врёт», пока его не перезапишут.
  - `Offset`/`Size` обрываются при любом сдвиге/ресайзе в layout.
- **Проверено на пикселях** (`SukiUI.Motion.RenderTests/CompositionOpacityTests`, headless + Skia):
  `InvalidateVisual` посреди fade — fade **продолжается** (серый 83 → 136); `Visual.Opacity = 0.99`
  посреди fade — обрыв и сразу 0.99 (79 → 3).
- **Ловушка (найдена на пикселях, 2026-10-02).** Изменить `Visual.Opacity` и **в том же кадре**
  вызвать `StartAnimation("Opacity")` — анимация **не стартует вообще**: синхронизация при рендере
  пишет `comp.Opacity` после `StartAnimation` и снимает ещё не отправленную анимацию (серый 0 через
  0.8 с). Первая версия сцены C2 делала именно так («Запустить» сбрасывал `Opacity = 1`) — после
  клика «0.99» сцена переставала работать; отсюда наблюдение пользователя «C2 не работает».
  **Для composition-бэкенда:** не менять свойство `Visual` и не стартовать composition-анимацию того
  же свойства в одном кадре (сброс — отдельным кадром).
- **Проверка:** сцена C2 (4 сценария рядом).

### 7.5. Анимированное значение нельзя прочитать на UI-потоке

- **Факт.** Клиентский геттер возвращает клиентское поле. Серверный readback
  (`TryGetValidReadback`) — `internal`.
- **Для нас:** прерывание с переносом позы и скорости (ключевая фича движка) требует **своей
  модели траектории** на UI-потоке: поза/скорость считаются аналитически, а не читаются.
- **Проверка:** сцена C3.

### 7.6. Нет событий завершения и нет пружин — но есть пользовательский easing

- **Факт.** Ни у анимаций, ни у визуала нет события «анимация закончилась». Встроенных
  пружин / natural motion нет.
- **Факт.** `InsertKeyFrame(progress, value, IEasing)` принимает любой `IEasing`, а
  `Avalonia.Animation.Easings.Easing` реализует `IEasing` → наш easing вычисляется **на потоке
  рендера**. `keyProgress` зажимается в [0, 1], результат easing — **нет** (перелёт пружины
  работает; NaN/∞ → кадр пропускается).
- **Ловушка.** `InsertKeyFrame` без easing берёт `Compositor.DefaultEasing` =
  `SplineEasing(0.25, 0.1, 0.25, 1)`, **не линейный**.
- **Факт.** Анимация стартует от текущего серверного значения (`Initialize(committedAt, field)`)
  — непрерывность позы при прерывании даётся бесплатно, непрерывность скорости — нет.
- **Факт.** Время старта — момент коммита пакета на сервере (`committedAt`), не `SukiTicker.Now`
  → модель и экран расходятся примерно на кадр.
- **Для нас:** пружину можно отдать композитору как **один keyframe с easing = точное решение
  пружины** (с начальной скоростью) на заранее вычисленную длительность до settle. Settle-колбэк —
  таймер на UI-потоке на ту же длительность. Easing-объекты должны быть неизменяемыми
  (вызываются с потока рендера).

### 7.7. Хит-тест и геометрия

- **Факт.** Хит-тест (`CompositionTarget.TryHitTest`) идёт по серверному readback-у — по тому, что
  реально нарисовано, **включая** composition-трансформы (с задержкой до кадра). *В ревью я
  предполагал обратное — ошибался.*
- **Факт.** `TransformToVisual` / `TranslatePoint` считаются по `Bounds` + `RenderTransform`
  (`VisualExtensions.GetOffsetFrom`) — composition-трансформы **не видят**.
- **Для нас:** под composition-сдвигом хит-тест честный, а код, который считает позиции
  (попапы, drag, `TranslatePoint`), видит layout-позицию.
- **Проверка:** сцена C4.

### 7.9. `CompositionCustomVisualHandler` — не для нас (сейчас)

- Даёт кадровый колбэк на потоке рендера, но только для **своего** рисования: свойства других

### 7.10. Замер C1: движок на UI-потоке без нагрузки (2026-10-02)

- **Как мерили.** `SukiUI.Motion.Playground --measure-c1 <файл> 6`: сцена C1, прогрев 1.5 с, затем 6 с
  записи времени каждого dispatch движка и начала каждого полупериода (`FrameMeasurement.cs`). Два
  прогона, машина пользователя (монитор ~144 Гц), UI-поток свободен.
- **Результат (оба прогона совпали):**
  - ≈ **144 dispatch/с**, интервал медиана 7.00 мс, σ ≈ 0.5 мс, max ≈ 14.5 мс, интервалов > 20 мс — **0**.
  - Отклонение интервала > 1.5 мс — у 0.8–1.3 % кадров.
  - Полупериод **701.3 мс** против 700 (composition — ровно 700 по серверным часам).
- **Выводы.**
  - Без нагрузки движок на UI-потоке **не теряет кадры** и идёт с частотой монитора. Путь RAF через
    завершение пакета композиции (§1.2) держит темп рендера.
  - Каждый перезапуск через `Then` теряет ~1.3 мс: следующий полупериод стартует с кадра settle, а не
    с теоретического конца предыдущего → фазы расходятся (~0.19 %, ≈ 0.1 с за минуту). После
    «залипания» UI-потока верхний квадрат сдвигается по фазе навсегда (`TimedTrajectory` считает по
    абсолютному времени → после паузы сразу `t = 1` → settle → новый полупериод от «сейчас»). Это
    объясняет впечатление «composition чуть быстрее» — он **впереди по фазе**, а не быстрее.
  - Зацикливание через `Then` в принципе неточно по времени → для повторов нужен примитив с точным
    расписанием (repeat/sequence, PLAN A9).
- **Не измерено.** «Плавнее»: интервалы UI-потока ровные, поэтому разница — между моментом расчёта
  позы (колбэк на UI-потоке) и моментом показа кадра (поток рендера). С UI-потока это не видно.
  Способ измерить — зонд на потоке рендера: `CompositionCustomVisualHandler.OnAnimationFrameUpdate`
  даёт время каждого кадра рендера (`CompositionNow`) → сопоставить с dispatch-ами UI (фаза 3, P2).

### 7.11. Порядок трансформов на сервере

- **Факт.** `MatrixUtils.ComputeTransform` (вызов в `ServerCompositionVisual.ComputedProperties.cs`)
  в порядке применения к точке: `-AnchorPoint·Size` → `TransformMatrix` (наш `RenderTransform` с его
  `RenderTransformOrigin`) → `Scale` вокруг `CenterPoint` → `RotationAngle` вокруг `CenterPoint` →
  `Orientation` → сдвиг на `Offset + Translation`. Комментарий в коде: математика повторяет
  *наблюдаемое* поведение UWP.
- **Для нас.** composition `Translation` = наш TranslateX/Y (в системе родителя). composition `Scale`
  применяется ПОСЛЕ `RenderTransform`: если UI-каналы держат rotate/skew, а scale уходит на composition,
  порядок меняется (scale·rotate вместо rotate·scale). `CenterPoint` надо ставить самим (аналог
  `RenderTransformOrigin`) и обновлять при смене размера.

### 7.12. Запись равного значения не останавливает анимацию (проверено на пикселях)

- **Факт.** `visual.Translation = (0,0,0)` во время composition-анимации, стартовавшей с `(0,0,0)`,
  **ничего не делает**: клиентское поле уже равно 0, сеттер запись пропускает, анимация едет дальше
  (`CompositionChannelTests.Raw_api_equal_write_does_not_stop_a_running_animation`: квадрат на 62 px).
- **Для нас.** Прототип делает статические записи принудительными: сначала «соседнее» значение, потом
  нужное — в пакет уходит только последнее (`CompositionSurface.SetStatic`). Последний keyframe —
  точная финальная поза, поэтому в покое сервер и клиент совпадают.

### 7.13. Прототип composition-бэкенда (D21): результаты пиксельных тестов

- `EaseTo` доезжает до цели (100 ± 1 px), `SpringTo` оседает на цели (120 ± 1 px), `Settled` — ровно
  один раз, в расчётный момент (1.28 с для ω=18, decay=20).
- **Прерывание без скачка:** до переключения 213 px, сразу после — 213, через 40 мс — 214 (инерция:
  пружина назад разворачивается постепенно), затем оседает в 0.
- Две оси одного свойства (`Translation`) анимируются независимо, ось Y стартует посреди полёта X.
- `Scale` 2.0 вокруг `RenderTransformOrigin`: ширина ровно 80 px, центр на месте.
- Модель (`CurveTests`): точное решение против RK4 — совпадение до 1e-8 по позиции во всех режимах.

### 7.14. Замер стоимости: движок против прототипа (2026-10-02)

- **Как мерили.** `SukiUI.Motion.Playground --measure-cost <файл> <N> 6`: N квадратов, каждые 400 мс
  все получают пружину к новой случайной цели (ω=10, decay=6, ζ=0.3 — пружина дольше 400 мс, так что
  почти каждый старт — прерывание с переносом скорости). Фазы подряд в одном процессе: простой →
  движок → прототип, по 6 с после 1 с прогрева. CPU процесса = все потоки (UI + рендер).
  Машина пользователя, 16 логических ядер, монитор ~144 Гц.
- **Первая версия прототипа (фиксированный шаг 4 мс):** CPU процесса ниже на 15–20 %, но **UI-поток
  нагружался сильнее, чем движком**: 67 мс/с (200 шт.) и 175 мс/с (600 шт.) на запуски против
  22 / 61 мс/с покадровой работы движка. Причина: ~1000+ ключевых кадров на старт — почти все на
  длинном почти неподвижном хвосте пружины.
- **После адаптивной сетки (`KeyFrameGrid`, D22):**

  | | 200 шт. | 600 шт. |
  |---|---|---|
  | UI-поток, запуски прототипа | 15–16 мс/с | 47 мс/с |
  | UI-поток, dispatch движка (только колбэки) | 18.5 мс/с | 55 мс/с |
  | CPU процесса, движок | 37–46 % ядра | 64 % |
  | CPU процесса, прототип | 25–27 % ядра | 48 % |

- **Выводы.**
  - Общий CPU прототипа ниже на ~25–45 %; у движка вдобавок не учтены в «dispatch» запись свойств,
    инвалидация и сериализация пакета на каждом кадре.
  - Стоимость прототипа — не покадровая, а **пачками на старт**: ~30 мкс на старт (600 стартов ≈ 19 мс
    раз в 400 мс). Для обычного UI (единицы–десятки одновременных стартов) пренебрежимо; для «сотни
    объектов разом» — короткая запинка UI-потока, при этом сама анимация на потоке рендера идёт ровно.
  - Замер шумный (движок 37 vs 46 % в двух прогонах) — сравнивать диапазоны, не точки.
  - Дальнейшее снижение: относительные пороги settle (P8) укоротят хвост пружины → меньше кадров.

### 7.15. Composition-анимация стартует только с коммитом — а коммит делает UI-поток

- **Факт.** `StartAnimation` лишь кладёт анимацию в очередной пакет. Пакет отправляется композитору в
  `Compositor.CommitCore`, который вызывает `MediaContext` в проходе рендера — **задачей на UI-потоке**
  (`RequestCompositionBatchCommitAsync → _triggerCommitRequested → MediaContext`). Сервер отсчитывает
  анимацию от момента коммита (`CompositionBatch.CommittedAt`, internal), а не от вызова.
- **Следствие.** Запуск и синхронная тяжёлая работа **в одном обработчике** → анимация не двигается всю
  эту работу (она ещё не отправлена) и проигрывается целиком после. «Немного туда-обратно» во время
  такого «сна» — это доигрывает **предыдущая** анимация, уже бывшая на сервере. Именно это увидел
  пользователь в сцене P1 («composition тоже замирает»).
- **Как измерили (в настоящем окне).** `--measure-stall`: после сна 1 с сканируем ряд хит-тестами — хит-тест
  идёт по серверному readback (§7.7), т.е. показывает, где квадрат реально нарисован.
  - A — `SpringTo`, затем сон в том же обработчике: сразу после сна нарисован **на 0**, затем проигрывает всю
    пружину с начала (перелёт 386+). Старый прототип при этом думал «314» → модель убегала на весь сон.
  - B — `SpringTo`, `await RequestCommitAsync()`, затем сон: анимация шла **во время** сна (сразу после
    сна — 316 при модели 315), дальше совпадение 1–2 px.
- **Публичный выход для вызывающего кода:** `await compositor.RequestCommitAsync()` (в прототипе —
  `CompositionMotion.CommitAsync()`) между запуском и тяжёлой работой. Для SukiUI это значит:
  например, хост диалога должен «отпустить» UI-поток на коммит перед синхронным построением контента.
- **Правильная привязка времени в движке.** `Compositor.RequestCompositionUpdate(Action)` (public)
  вызывает колбэк на UI-потоке **непосредственно перед** коммитом, внутри `CommitCore` — ровно в
  момент, от которого сервер отсчитывает анимацию. Прототип строит ключевые кадры и перевыставляет
  время старта кривых там (D23). Первая попытка — метка времени с потока рендера по
  `Batch.Processed` — **неверна**: в headless обработка пакета ждёт тика рендера, и сдвиг получался
  ложным (180 мс вместо миллисекунд), ломая инерцию при прерывании.
- **Задержка readback.** Хит-тест видит последний ОТРИСОВАННЫЙ кадр: на скорости ~1500 px/с модель
  опережает «нарисованное по хит-тесту» на 15–25 px (≈ кадр). Это свойство измерителя, не рассинхрон.
